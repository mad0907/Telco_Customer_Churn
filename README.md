# Telco Customer Churn -- Predictive Modeling, Deployment Architecture, and Governance

Churn prediction for the IBM/Kaggle Telco Customer Churn dataset, built as a
production-oriented exercise rather than a single notebook: an executed
analysis notebook, a written report with a deployment/governance blueprint,
and a small interactive prototype, all backed by the same trained model.

## What is in this repository

| Path | What it is |
|---|---|
| `notebooks/telco_churn_analysis.ipynb` | The full analysis: data audit, EDA, feature engineering, three models (Logistic Regression, Random Forest, XGBoost), evaluation (including a bootstrap confidence interval, lift/gain, and risk segmentation), SHAP interpretation, and a monitoring plan. Already executed -- outputs and charts are saved in the file. |
| `docs/Telco_Churn_Writeup_and_Architecture.docx` | The write-up: results, recommendation, and a full deployment/architecture/AI-governance blueprint for putting this model into production on Azure. |
| `docs/API_REFERENCE.md` | Reference for every module and function in this repository -- what each one does and why, including the ones not safe to auto-document with `pydoc` (they run real work at import time). |
| `docs/pydoc/*.html` | Real `pydoc`-generated HTML for the three modules that are safe to auto-import (`churn_features`, `pipeline_dev`, `modeling_dev`). Regeneration command is at the bottom of `API_REFERENCE.md`. |
| `app.py` | A Streamlit prototype: enter a customer profile, see the churn prediction, risk tier, SHAP drivers, and a recommended action. Loads the model the notebook trains and saves -- it does not retrain. |
| `src/churn_features.py` | Shared data-cleaning and feature-engineering functions, used by `app.py`. |
| `src/*.py` (other files) | The scripts that generated the notebook, the architecture diagrams, and the Word document, kept for reproducibility and transparency. |
| `models/` | The persisted model artifact and its metadata. Created by running the notebook -- not committed empty. |
| `deployment/` | Illustrative Azure ML / MLOps configuration: training pipeline, managed online endpoint, scoring script, CI/CD pipeline, monitoring job, and the immutable-audit-logging design. These are blueprint-quality YAML/Python, written to be correct and complete, not executed against a live Azure subscription as part of this exercise. |
| `assets/` | The architecture, MLOps, and governance diagrams (as PNGs) referenced in the write-up. |
| `data/WA_Fn-UseC_-Telco-Customer-Churn.csv` | The source dataset. |
| `requirements.txt` | Pinned Python dependencies. |

## Setup

Requires Python 3.11+.

```bash
python3 -m venv venv
source venv/bin/activate          # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Running things

### Read the analysis

To simply open the notebook and look through it (it has already been
executed end to end, so all charts and results are visible without
rerunning anything):

```bash
jupyter notebook
# or: jupyter lab
```

Then open `notebooks/telco_churn_analysis.ipynb` from the browser tab that
opens. Uploading the file to Google Colab works the same way.

To re-execute it yourself instead (regenerates `models/` in the process,
which the Streamlit app and the write-up build script both depend on):

```bash
jupyter nbconvert --to notebook --execute --inplace \
  notebooks/telco_churn_analysis.ipynb
```

### Run the interactive prototype

The app loads the model persisted by the notebook, so run the notebook at
least once first (or use the `models/` artifacts already included in this
delivery).

```bash
streamlit run app.py
```

Opens at `http://localhost:8501`. Use the "Load an example customer"
dropdown for a quick demo, or fill in a profile manually.

### Read the write-up

Open `docs/Telco_Churn_Writeup_and_Architecture.docx` in Word (or any
compatible viewer). It stands alone -- it does not require running any
code.

## Regenerating the notebook, diagrams, or write-up from source

The notebook, the architecture diagrams, and the Word document are all
generated by scripts in `src/`, rather than hand-edited directly. This
keeps the analysis reproducible: change the modeling code, rerun the
pipeline below, and both the notebook and the write-up reflect the new
results automatically -- there is no step where a number has to be
manually copied from one file into another.

```bash
cd src
python build_notebook.py          # writes notebooks/telco_churn_analysis.ipynb (not executed yet)
jupyter nbconvert --to notebook --execute --inplace \
  ../notebooks/telco_churn_analysis.ipynb            # executes it, writes models/*.joblib and models/metrics.json
python build_diagrams.py          # writes assets/*.png
python build_writeup_doc.py       # reads models/metrics.json, writes docs/Telco_Churn_Writeup_and_Architecture.docx
```

The notebook exports every headline number quoted in the write-up (model
metrics, lift, risk-tier rates, the cost-sensitive comparison) to
`models/metrics.json` in its last section. `build_writeup_doc.py` reads
that file to populate its tables rather than having any numbers typed into
it directly -- it will refuse to run (with a clear error) if
`models/metrics.json` doesn't exist yet, which is a reminder to execute the
notebook first, not a bug. Run order matters: `build_notebook.py` →
execute the notebook → `build_writeup_doc.py`.

## Deployment folder

`deployment/` is a blueprint, not a deployed system -- it documents how the
recommended model would be operationalized on Azure ML (training pipeline,
managed online endpoint, CI/CD, monitoring, and an immutable prediction-
audit design using Azure Confidential Ledger and Key Vault). None of it
requires an Azure subscription to review; it is meant to be read alongside
Part II of the write-up.

## Notes

- No client branding, logos, or proprietary material is used anywhere in
  this repository -- the dataset is the public Kaggle Telco Customer Churn
  dataset.
- `deployment/score.py`'s audit-logging call (`append_to_ledger`) is
  illustrative -- it references a `governance_client` module that is
  intentionally not included, since it would need to be implemented against
  a real Azure Confidential Ledger instance. The design it implements is
  documented in `deployment/governance_logging.md`.
